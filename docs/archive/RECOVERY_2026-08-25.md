# Soil Sensor System Recovery Report — 2026-08-25

**Incident window:** 2026-08-23 15:44 EDT → 2026-08-25 20:20 EDT
**Outcome:** Full stack restored, no data lost. 5 of 9 sensors returned to service; 4 blocked on a DHCP fault requiring physical access.

---

## Executive Summary

Two **independent** failures landed within a day of each other, and their overlap is what made this hard to diagnose:

1. **2026-08-23 15:44** — an InfluxDB token rotation updated `panel-health.env` but not the Grafana datasources or the sensor firmware. Dashboards broke immediately; every sensor stopped writing at **19:44Z** that evening.
2. **2026-08-24** — the Raspberry Pi's microSD card failed with I/O errors. Unrelated and coincidental.

The presenting symptoms ("InfluxDB token issue" + "Grafana down" + "can't SSH") looked like one cascading failure. They were not. All InfluxDB and Grafana data survived because it lives on a separate USB drive.

## Root Cause 1 — Revoked InfluxDB token

The rotation created three tokens (`grafana + alerting (read-only)`, `system-metrics-collector (write)`, `operator replacement`) and revoked the previous one. Two consumers still held the revoked token:

- **Grafana datasources** — stored token rejected:
  ```
  {"message":"unauthorized: unauthorized access error reading buckets","status":"ERROR"}
  ```
- **Sensor firmware** — `INFLUX_TOKEN` is a compile-time `#define` in `firmware/src/secrets.h`, used by `database_client.cpp:125`, `heartbeat.cpp:94` and `diagnostics.cpp:291`. A rotation on the Pi silently cuts off every sensor until each board is reflashed. Confirmed: the firmware's token returned `401` against `/api/v2/buckets`.

**Fix:** repointed all datasources at `http://influxdb:8086` with the valid read token; minted a dedicated write-only token for the firmware and reflashed.

Worth noting: the surviving `panel-health.env` token can read but **cannot create authorizations** (`write:orgs/.../authorizations is unauthorized`). The token able to mint new ones is `INFLUX_ADMIN_TOKEN` in `backup.env`.

## Root Cause 2 — microSD card failure

**Symptoms, in the order they appeared:**

- SSH died before the version banner:
  ```
  kex_exchange_identification: read: Connection reset by peer
  ```
  TCP connected, but sshd could not fork a session. Grafana and InfluxDB kept serving because they were already resident in memory with their data on the USB drive.
- Then, at the console:
  ```
  bash: /usr/bin/ls: Input/output error
  ```
  The kernel could no longer read binaries off the card.

**Confirmation on another machine.** With the card in a Mac reader, `cmdline.txt` read back as **214 bytes of `0xff`** — the erased state of NAND — while `config.txt` beside it was intact. A 48 MB write round-tripped perfectly and a 214-byte file written by macOS read back correctly, so this was **selective bad-block corruption**, not a dead card or a driver artefact.

That also explains the emergency-mode boot: `cmdline.txt` carries `root=PARTUUID=...`, so the kernel got nothing usable.

### The wasted cycle — worth recording

The first reflash went to **the dying card, not the new one**. The old card had been logically ejected but was still physically in the reader, and both cards were 256 GB, so they were indistinguishable in the imager's storage list. The result was a second emergency-mode boot and roughly an hour lost.

**Lesson:** physically remove the failed card before flashing, and prefer a different capacity for the replacement so the two can never be confused. The replacement is 32 GB against the old 256 GB — now unambiguous.

## What survived, and why

`/mnt/sensor-data` is a **separate 256 GB USB drive** (label `sensor-data`, UUID `1efa7d23-…`), holding both `influxdb/data/` and `grafana/data/`. It was never touched. All 7 dashboards, all 3 datasources, and the full metric history came back intact.

Only the SD card was lost, and everything on it was reproducible: OS, systemd units, tokens, and the Cloudflare tunnel credentials.

## Recovery procedure (as actually followed)

1. Diagnose remotely — confirm the box is alive and only sshd is broken.
2. Console access; confirm I/O errors; **do not reboot** while salvaging.
3. Power off cleanly, image a **new** card with Raspberry Pi OS 64-bit, SSH + public key enabled.
4. Boot with the USB drive **unplugged** to isolate variables.
5. Mount the data drive by UUID with `nofail`; inventory before starting anything.
6. Install Docker; bring up InfluxDB and Grafana **pinned to the versions that were running** (`influxdb:2.7.12`, `grafana/grafana:13.0.2`). A newer image migrates `influxd.bolt` / `grafana.db` one-way.
7. Back up both databases *before* any container touches them.
8. Repoint datasources; verify with a real query, not just a health check.
9. Recreate the Cloudflare tunnel (credentials cannot be re-downloaded).
10. Reinstall the metrics collector and the backup timer.
11. Reflash sensors **individually**, verifying each writes to InfluxDB.

### 1. Backups had produced nothing since 2026-05-20

Four independent problems, each sufficient alone:

- `sensor-backup.service` set no `EnvironmentFile`, so `INFLUX_ADMIN_TOKEN` was never set and the script exited at its first guard.
- The `influx` CLI is absent from the host because InfluxDB runs in Docker.
- `if influx backup ...; else log "failed"; fi` **swallowed the error** — the script still exited 0, so systemd recorded success.
- Nothing alerted on failure, despite Slack alerting being available.

The backup now exits non-zero, raises a Slack alert, and verifies the output directory is non-empty rather than trusting the exit code. `install-influx-cli.sh` lifts the binary out of the InfluxDB image so its version always matches the server and never depends on InfluxData's APT repo (which fails GPG verification on Trixie).

### 6. The flash script would have destroyed per-plant history

`flash-ota-canary.sh` built **one** binary and flashed it to every sensor, while `DEVICE_ID` / `DEVICE_LOCATION` are per-sensor `#define`s in `config.h` (`DEVICE_ID_AUTO` is declared but never referenced in the firmware). Running it would have stamped all nine devices as `sensor-9`/`guest-room`.

Three further defects: no `-e esp8266-ota` so it selected the wrong environment; `config-helpers.sh` reads only `.sensors[]`, making the two climate boards invisible; and `declare -A` does not exist in macOS's bash 3.2, so it could not run on the machine it targets.

**A subtlety that matters:** a plain `#define` in a header **wins over** a `-D` build flag (verified with `cc -E`: the flag is discarded with only a `macro redefined` warning). Per-sensor builds therefore require `#ifndef` guards in `config.h` — without them every binary would have been identical while appearing to build correctly.

### `DEVICE_TYPE` — caught in production

The working tree had `#define DEVICE_TYPE DEVICE_TYPE_CLIMATE` (left from configuring sensor-9). Flashing soil probe sensor-7 while overriding only `DEVICE_ID` and `DEVICE_LOCATION` compiled the **soil path out entirely** — the board came back reporting `{"error":"no data"}` and wrote heartbeats but no `sensor_reading`.

`DEVICE_TYPE` is now `#ifndef`-guarded with a **soil** default, derived per device from which array it occupies in `sensors-config.json`, and verified in the built ELF **before upload** by counting linked `_ZN3DHT` symbols — string markers are unreliable because the web dashboard embeds both `moisture=` and `humidity=` regardless of type.

### 7. Unmounted-drive shadowing (the most dangerous)

Beyond the wrong paths, the compose file left the original "all the data is gone" failure mode wide open. `/etc/fstab` mounts the drive with `nofail`, `docker.service` has no ordering dependency on that mount, and both containers use `restart: unless-stopped` — so the daemon starts them at boot without Compose. Raw bind mounts **auto-create** their source directory. A boot where `/dev/sda1` is absent would have Docker create empty directories on the SD card, Grafana initialise a fresh empty `grafana.db`, InfluxDB come up unconfigured, and the real data shadowed by a live mount.

Both binds are now **bind-backed named volumes**: the local driver's bind option does not auto-create, so Docker refuses to start and the failure is loud. Images are pinned **by digest**, since tags are mutable and get re-pushed for base-image rebuilds.

### 8. Dashboard panels that could never return data

- `rpi-health.json` / `system-health.json` filtered `_field == "memory_percent"` — a field that has **never existed**. The collector writes `ram_percent`.
- `alerts-overview.json` called `experimental.subDuration()` without importing the package, so the query failed to compile.
- `alerts-overview.json` hardcoded the expected sensor count as `4` in two places, producing a negative offline count and a health score above 100%.
- `soil-moisture-main.json` "System Status" had its green threshold at `9`, but only seven soil sensors exist — a healthy system was permanently yellow.

## Known issues

**Four sensors are offline on a DHCP fault, not a firmware fault.** sensor-5, sensor-6, sensor-8 and sensor-9 are alive on the L2 network but failed to obtain leases and fell back to APIPA link-local addresses (`169.254.x.x`, confirmed by ARP). Notably **sensor-8 was never reflashed** and fell into the same state on its own, which exonerates the flash process. They need a power cycle; if it recurs, check the router's DHCP pool.

**The OTA password is still in git history** and appears in eight tracked files. It was moved out of `main.cpp` and `platformio.ini`, but the value should be **rotated** now that the fleet is being reflashed. Rotating requires care: sensors authenticate with the *old* password until they run the new firmware, so the build must compile the new password while the upload uses the old one.

**One orphaned Grafana datasource** (`PB4A2C00F7BB2A2DA`) remains, provisioned and read-only, pointing at `localhost:8086`. No dashboard references it. Harmless but untidy; it cannot be edited via the API.

## Preventive actions

### P0 — Token rotation runbook
Rotating an InfluxDB token must update **three** consumers together, or sensors go silent with no alert:
1. Grafana datasources (API, or the UI)
2. `firmware/src/secrets.h` → rebuild → reflash every board
3. `~/soil-sensor/system-metrics.env` → restart the collector

Always **create and verify** the new token before revoking the old one.

### P0 — Backups must fail loudly
Done. Keep the Slack alert path working; a backup that cannot alert is a backup you will discover is missing during an incident.

### P1 — Filesystem protection for SD write wear
This is the **third** storage incident (`STORAGE-ROOT-CAUSE.md`, and `influxdb.corrupted.20260522_070452` on the drive). Run `rpi-setup/install-filesystem-protection.sh`.

### P1 — Alert on sensor silence
Every sensor stopped for **two days** before anyone noticed. `check-sensor-health.sh` exists; make sure it is installed and alerting after a rebuild.

### P2 — Complete `sensors-config.json` consumers
The file already describes all nine devices; the flash tooling read only seven. Any new tooling must read `.sensors[]` **and** `.climate_sensors[]`.
